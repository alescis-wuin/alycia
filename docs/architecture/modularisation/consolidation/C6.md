Les méthodes peuvent appeler d’autres domaines après construction. Les chemins suivants ont été vérifiés.

- `EfChatRepository.ContextFilesAsync` appelle `DocumentAnalysisService.MetadataAsync` et `StructuredMemory.Hash`. `DocumentAnalysisService` et `ConversationFiles` créent un `EfChatRepository` sur leur DbContext pour enregistrer la révision. Les références de types Conversations ↔ Documents existent déjà.
- `IndexMaintenance → ITemporalMemoryIndex → TemporalMemoryStore → IIndexedEmbeddings → IndexedEmbeddingSearch → OllamaEmbeddings`. Il n’y a pas de retour vers la maintenance. Regrouper ces objets en deux noms de domaines ferait apparaître Indexation ↔ Mémoire. Les projets et la résolution des services restent acycliques.
- `ProjectToolService` crée `HistoryTools(new EfChatRepository(database), …)`. `HistoryTools` emprunte `ProjectRetrieval.Bm25`, `StructuredMemory.Hash` et le type de passage `SourceChunk`. `TurnTools.GenerateAsync` reçoit le modèle en paramètre. `ProjectMcpClient` est hébergé dans l’API, hors du namespace d’application.
- `TurnContext.BuildAsync` reçoit le modèle et appelle les fonctions de contexte, `TemporalMemory` renvoie un `PreparedContext`, et `ConversationMemory.Apply` consomme le résultat de la préparation. Une séparation physique naïve Contexte/Mémoire introduirait un besoin de contrat commun.
- `WorkspaceSources.ForConversation/ModelSources` conserve l’appartenance, les exclusions et la priorité des réglages locaux pour le dépôt, les outils et l’index. Le classement consomme l’instantané filtré. `ProjectRetrieval.Reference` est aussi utilisé dans l’index et les outils pour stabiliser les références.

## Coût et candidats

| Candidat | Gain possible | Coût ou condition concrète |
|---|---|---|
| Adaptateurs Ollama | Six fichiers, deux clients concrets, compilables contre Application et Contracts avec la seule BCL. Aucun accès EF ni paquet externe direct dans ces six fichiers. | Un consommateur de production nomme ces types, `ChatRegistration`. Cinq fichiers de tests les nomment à C0, mais le projet de tests commun garde les références à l’API et à Infrastructure. La substitution est déjà possible via les ports. Un consommateur autonome ou une campagne isolée apporterait un bénéfice complet. |
| Documents | Les extracteurs pourraient former un ensemble isolé avec PdfPig. | L’import et l’analyse demandent EF, stockage, exclusions partagées, révision et checkpoint. Le lecteur et les références des sources servent aux autres domaines. Séparer le seul extracteur n’isole pas les opérations de persistance. |
| Indexation | Un exécuteur indépendant pourrait exploiter les tâches persistées. | Le worker in-process, la priorité du chat, `ITemporalMemoryIndex`, les unités partagées, les sources et les vecteurs traversent déjà plus d’une frontière. Déplacer les classes ne découple pas la planification. |
| Retrieval | Le classement pur est isolable, l’adaptateur ONNX concentre deux paquets spécifiques dans un fichier. | L’adaptateur est construit par le host, référencé par un test et par le benchmark. Enregistrer le même adaptateur dans le host conserve les bibliothèques natives distribuées. Le corpus et `SourceChunk` restent nécessaires. |
| Contexte | Scénarios de préparation déjà testables via ports simulés. | Messages, `PreparedContext`, mémoire, estimation, outils et routage sont partagés. L’extraction du seul dossier perdrait des implémentations placées à la racine d’Application. |
| Mémoire | Le moteur de sélection pure dispose de tests séparables. | Le dépôt conserve la sémantique atomique du tour, la lecture temporelle utilise les index, les unités et la recherche lexicale. Un contrat neutre pour les résultats de préparation serait préalable. |
| Outils | Le client MCP a déjà son port interchangeable. | La branche snapshot lit le même DbContext que le tour. Kestrel reste propriétaire du transport loopback. Séparer un projet ne crée pas de nouveau consommateur ou de meilleure isolation du snapshot. |
| Conversations | Orchestration indépendante des adaptateurs par interfaces. | La fourche coordonne originaux et base et le tour coordonne mémoire et messages. Une extraction du dossier ne déplace ni le propriétaire transactionnel, ni les types nécessaires à tous les autres modules. |

Les 8 `PackageReference` directs de Chat.Infrastructure comprennent EF/Npgsql, Roslyn, PdfPig, ONNX Runtime et le tokenizer. Chat.Application n’en déclare aucun. Le Dockerfile copie explicitement les huit projets utilisés pour restaurer l’API, puis leurs sources pour la publication. Toute extraction effective exige la mise à jour des deux séries de `COPY`, du graphe et du projet de l’appelant. Le client conserve sa seule référence Contracts.

### Vérifier le graphe de composition

Cette vérification a trié les 36 services ci-dessus et leurs 61 dépendances. Une dépendance non classée ou un cycle provoque un échec. Pour réexaminer les arêtes, confronter la table aux constructeurs et aux fabriques via `rg -n 'AddScoped|AddSingleton|AddHttpClient|AddHostedService|GetRequiredService' src/Alycia.Api/Chat/{ChatRegistration,EmbeddingWorker}.cs`.

```python
from graphlib import TopologicalSorter
from pathlib import Path
import sys

text = Path(sys.argv[1]).read_text().split("```text\n", 1)[1].split("\n```", 1)[0]
owner, edges = {}, {}
for line in text.splitlines():
    group, service, dependencies = (value.strip() for value in line.split("|"))
    owner[service] = group
    edges[service] = dependencies.split()
assert {dep for deps in edges.values() for dep in deps} <= owner.keys()
reachable = {}
for service in TopologicalSorter(edges).static_order():
    reachable[service] = {target for dep in edges[service] for target in [dep, *reachable[dep]]}
for group in dict.fromkeys(owner.values()):
    nodes = [key for key in owner if owner[key] == group]
    direct = {owner[dep] for key in nodes for dep in edges[key]} - {group}
    indirect = {owner[dep] for key in nodes for dep in reachable[key]} - direct - {group}
    print(group, sorted(direct), sorted(indirect))
print(len(edges), sum(map(len, edges.values())))
```
