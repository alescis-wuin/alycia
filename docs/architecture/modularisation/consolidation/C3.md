# C3 — Admission des annotations Ollama

## Décision et portée

Sur la référence C0 `118c9186d08f731763ad583a4de4051e8512c716`, une requête interactive peut attendre derrière le lot d’embeddings en cours **et les trois annotations déjà soumises**. Les barrières du test reproduisent cet ordre sur les vrais adaptateurs HTTP avec un fournisseur simulé. Le premier delta du chat arrive après 161,23 ms en médiane sur cette charge.

Le transport limite désormais à une l’annotation admise en attente ou en exécution dans le sémaphore commun. À la libération, il rend d’abord le permis physique, puis l’admission des annotations. Le chat et les embeddings continuent à accéder directement au permis physique. Le premier delta du même scénario arrive après 95,92 ms en médiane. Les trois annotations se terminent dans chaque séquence. Aucun traitement déjà actif n’est interrompu.

Le changement porte sur `Inference/OllamaInferenceLease.cs`, `Inference/OllamaChatModel.cs` et `Inference/OllamaChatModel.Streaming.cs` du projet Infrastructure. Les appels identifiés par le champ runtime existant `CallPurpose == "annotation"` passent par l’admission. Le nombre de travaux préparant des documents reste réglable par `Enrichment.Workers` (1 à 4). Un seul modèle travaille à la fois dans le processus. Ajouter un nombre de permis GPU ou un nouveau réglage persistant n’apporte aucun bénéfice démontré dans cette mesure.

## Durée de vie et priorité

| Mécanisme | Portée | Comportement vérifié ou visible dans le code |
|---|---|---|
| `GenerationGate.Shared.Enter(id)` | Conversation, dans le processus API | Exclusion du tour concurrent. `ChatService` vérifie d’abord replay et révision. |
| `PreferForeground()` | Compteur des tours actifs, après préparation des options | Le worker rend la main au démarrage d’un lot et entre lots. `KnowledgePass` vérifie la priorité avant de soumettre une annotation. Les jobs persistés reprennent après libération. |
| Admission d’annotation | Générations annotées, flux inclus | Une annotation au plus atteint le permis partagé. Les autres attendent avec le token de l’appelant. Une annotation déjà admise peut précéder le chat. |
| `OllamaInferenceLease` | Appels de génération et d’embedding du processus | Le délai actif démarre après acquisition. Chaque ligne complète du flux renouvelle le délai d’inactivité. L’annulation et les erreurs libèrent les permis acquis. |
| `EmbeddingWorker` | Scope par cycle, pause de 5 s | `IndexMaintenance` visite les travaux séquentiellement. Les préparations d’annotations d’un travail sont concurrentes, les lots de vecteurs sont délimités et la progression est persistée. |

La priorité de découverte n’agit pas rétroactivement sur les appels déjà soumis. La borne d’admission traite précisément ce cas. Le scénario avec un nombre fini de requêtes démontre la progression des deux classes. Une suite ininterrompue de tours peut maintenir le worker différé par sa politique existante. L’ordre FIFO général, les interactions entre plusieurs processus et la latence d’un GPU réel restent hors des garanties mesurées.

## Mesure avant/après

Linux x86-64, AMD EPYC 9V74, 9 processeurs visibles, `DOTNET_PROCESSOR_COUNT=4`, SDK 10.0.404, runtime 10.0.15, configuration Debug. Aucun périphérique GPU disponible. VRAM réelle non mesurée. Les modèles `local` et `vectors` sont simulés en mémoire. Aucun poids ne se charge.

Une séquence occupe d’abord le modèle avec un lot de deux passages. Trois annotations de fichiers sont soumises, puis un chat en streaming sous réservation foreground. Une barrière libère le lot lorsque les quatre autres appels attendent. Le gestionnaire simulé renvoie deux vecteurs de dimension 2 ou le texte `ok`, avec un délai nominal de 30 ms par inférence. Délais actifs configurés de 5 s pour les générations et 180 s pour les embeddings. Un tour de chauffe est exclu, puis dix séquences sont mesurées avec l’horloge monotone.

L’attente va de la soumission à la première entrée HTTP dans le gestionnaire, métadonnées comprises. L’intervalle actif va de cette entrée à la préparation de la dernière réponse simulée. Le total inclut la lecture de la réponse par le client. Le premier delta est daté dans le rappel du consommateur NDJSON. Les p95 sur dix observations correspondent aux maxima de cette campagne. Les durées dépendent de la charge de l’hôte.

## Régression, annulation et reprise

- Sur C0, les deux nouveaux tests donnent 1 réussite et 1 échec. Le diagnostic est `3 already submitted annotations ran before the interactive stream`.
- Après correction, les 26 tests ciblés passent, aucun ignoré. Les assertions de la nouvelle suite utilisent l’ordre et les barrières, sans seuil de performance. Les données de temps sont activées à la demande.
- L’annulation d’une annotation en attente d’admission puis d’une autre en attente du permis physique ne touche jamais le fournisseur. Du signal d’annulation à l’observation de l’exception, respectivement 1,32 et 0,99 ms après correction sur un essai. Un refus HTTP 503 sur une annotation admise est suivi d’une annotation réussie et d’un flux interactif réussi.
- Les tests existants gardent le modèle occupé 1,3 s avec un délai de génération de 1 s. Les deux modes réussissent après libération. Une inférence active qui ne répond jamais expire, et l’appel suivant réussit. Le test PostgreSQL dédié vérifie le travail différé au premier plan, les tranches persistées puis leur achèvement, également en mode hybride.

Tests et instrumentation sont réunis dans `tests/Alycia.Modules.Chat.Tests/OllamaSchedulingTests.cs`. Mesure réexécutable hors base depuis le checkout de consolidation, avec un SDK .NET 10 :

```sh
env DOTNET_PROCESSOR_COUNT=4 ALYCIA_MEASURE_OLLAMA_QUEUE=1 \
  dotnet test tests/Alycia.Modules.Chat.Tests --filter 'FullyQualifiedName~OllamaSchedulingTests' \
  --logger 'console;verbosity=detailed'
```
