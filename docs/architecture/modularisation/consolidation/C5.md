# C5 — Réglages de la recherche vectorielle

Le travail isolé part de `118c9186d08f731763ad583a4de4051e8512c716`. La recherche vectorielle recevait un objet `ChatOptions` mutable. Si son propriétaire le modifiait pendant la résolution asynchrone de l’identité du modèle, l’encodeur suivant pouvait recevoir un autre modèle, un autre découpage ou un autre préfixe. Deux tests reproduisent cette incohérence par les entrées publiques, sur les documents et la mémoire.

## Changements retenus

- `EmbeddingSettings.ForQuery(IIndexSettings)` capture le profil avant la première attente. Les deux méthodes privées de calcul de `IndexedEmbeddingSearch` passent de deux paramètres typés `ChatOptions` à zéro. Elles ne reçoivent que le profil immuable existant. Le modèle d’une requête explicite reste utilisable lorsque le profil de tâche de fond réserve le travail à l’enrichissement.
- `EmbeddingSettings.RequiresJob(IIndexSettings)` centralise une décision présente à trois endroits, dans la découverte des conversations, celle des projets et la vérification du worker. Elle lit le mode, le modèle d’embeddings et l’activation de l’enrichissement. Le format du profil persisté et ses règles de révision restent identiques.
- Les ports publics conservent leurs signatures. L’import, le stockage de la configuration et l’édition de la conversation requièrent le schéma v1 complet. Le tokenizer, le plan et le suivi d’usage appartiennent aux options effectives du tour. Une nouvelle interface pour chacun de ces usages demanderait de modifier des contrats existants sans bénéfice démontré par ces changements.

## Preuves et reproduction

Avant la correction, les deux variantes de `EmbeddingQuerySettingsTests` ont échoué : un encodeur recevait `second` après le lancement de la recherche avec `first`. Une barrière de tâche suspend la résolution sans temporisation. Après correction, les assertions vérifient le modèle, le préfixe, un lot de deux fragments puis un lot d’un fragment et l’espace de vecteurs utilisé pour les trois recherches de similarité.

La première campagne sur PostgreSQL de test avec pgvector activé a réussi, 35 tests sur 35, aucun ignoré. Après avoir renforcé les cas v1, la seule classe modifiée a été rejouée, 15 sur 15. Le contrôle du fichier v1 compare les 2 074 octets générés à la fixture de référence, hors son LF final de fichier texte. Leur SHA-256 est `b1d22617099059db98ec9a44cefa109927067d1a1ed25182f601e77135a2751b`. Les tests couvrent le modèle d’index, les valeurs par défaut isolées par conversation, les champs transitoires, les valeurs nulles, un lot hors bornes et le rejet d’un format incomplet.

Avec une base de test dédiée et `ALYCIA_CHAT_TEST_CONNECTION` renseignée, le filtre final regroupe ces cas :

```bash
ALYCIA_TEST_PGVECTOR=1 dotnet test tests/Alycia.Modules.Chat.Tests \
  --filter 'FullyQualifiedName~EmbeddingQuerySettingsTests|FullyQualifiedName~EmbeddingIndexBoundaryTests|FullyQualifiedName~PersistentEmbeddingTests|FullyQualifiedName~KnowledgePipelineTests|FullyQualifiedName~ConfigurationTests|FullyQualifiedName~ConversationSettingsTransferTests'
```

Les contrôles vectoriels utilisent un encodeur simulé. L’éditeur continue à modifier le modèle v1. Le profil capturé couvre la durée de la recherche. Le SHA de livraison et la liste de ses fichiers s’obtiennent par `git log --diff-filter=A -1 --format=%H --name-only -- docs/architecture/modularisation/consolidation/C5.md` et `git show --name-only <SHA>`.
