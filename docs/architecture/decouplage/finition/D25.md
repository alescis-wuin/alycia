# D25 — Mémoire temporelle, sélection d’historique et commit du tour

**État de la reprise du 22 novembre 2026** — PARTIEL. Historique et rappel projetés. Context appelle directement StructuredMemory, TemporalMemory et la sélection de mémoire. [Bilan et preuves](D29-bilan-reprise.md)

## Passage initial

**PARTIEL.** Memory possède la persistance de temporal_memory, y compris la reprise d’un lot interrompu, le classement lexical, le filtre temporel strict, l’export et l’effacement transactionnel. Son adaptateur utilise la session PostgreSQL du tour. Les messages et les options de leurs propriétaires sont lus par deux projections paginées de Conversations. Un cycle récupère au plus 32 corps de messages par propriétaire. Une séquence déjà intégralement couverte dispense de relire les messages. La suppression concurrente du propriétaire n’est ignorée que pour sa contrainte de clé étrangère précise.

Context calcule la sélection de l’historique depuis des messages et budgets immuables, avec le compteur de tokens fourni par l’appelant. Le port est enregistré dans l’API. Conversations applique le PreparedMemoryChange du contrat dans son propre commit de tour. La configuration persistée et les migrations sont préservées.

Les 72 tests ciblés de contexte, mémoire, streaming et configuration passent avec PostgreSQL/pgvector. Un test supplémentaire a exécuté un lot de 32 sur 36 messages, supprimé un checkpoint puis vérifié la reconstruction complète et ordonnée des 36 séquences. Les deux assemblies Memory et Context compilent dans des répertoires isolés. La garde compilée accepte 23 projets. Quatre dérogations SQL/EF sont retirées (16 → 12).

La préparation récursive, l’assemblage de preuves, la sélection structurée et une partie du rappel restent dans Chat.Application et Chat.Infrastructure. L’isolation constatée des deux assemblies couvre les traitements effectivement déplacés. Le graphe logique complet comporte encore des cycles. Retour arrière par revert du commit D25.
