# Architecture overview

## Goals

Alicia separates conversation rules, application orchestration, external AI/provider integrations, shared Avalonia presentation, and executable platform hosts.

## Layers

### Domain

Framework-independent domain concepts and invariants. The conversation core owns typed conversation/message identifiers, normalized titles, creation/activity metadata, message roles, immutable message data, and aggregate-level lifecycle invariants.

### Application

Use cases and ports for response generation, provider lifecycle management, persistence, clocks, files, search, tools, and other external capabilities. The conversation application slice exposes creation, loading, summary listing, renaming, message appending, deletion, the provider-neutral `IConversationResponder` and `IStreamingConversationResponder` response ports, non-streaming generation/completion, streamed turn orchestration, and an `IConversationRepository` persistence port without selecting an infrastructure implementation. `IInferenceProviderRuntime` exposes provider detect/install/start/stop state plus a provider-neutral installation-progress contract without referencing llama.cpp, CUDA, processes, or HTTP. Providers that support managed updates may additionally implement `IInferenceProviderUpdateRuntime`, which exposes a validated version, explicit update checking, and explicit update execution through provider-neutral `InferenceProviderUpdateInfo` / `InferenceProviderUpdateResult` contracts. Providers with Alicia-owned storage may independently implement `IInferenceProviderMaintenanceRuntime`, which exposes read-only storage inspection plus explicit retained-release cleanup and uninstall scopes through `InferenceProviderStorageInfo`, `InferenceProviderMaintenanceResult`, and `InferenceProviderRemovalMode`. Providers that expose generation telemetry may independently implement `IInferenceProviderObservabilityRuntime`, whose immutable `InferenceProviderGenerationObservation` carries only provider/model/version identity, outcome/failure classification, latency, token counts, and optional provider timings. Application also owns immutable provider descriptors/configuration, generation options, the `Missing/Unsupported/Faulted/Network/Model` failure taxonomy, a safe-message `InferenceProviderException`, an explicit provider-registry port, and a configuration-store port. Both turn paths are tied to the triggering user-message identifier and share snapshot validation. Streaming distinguishes provider-neutral Content and Reasoning chunks, forwards both to Presentation, accumulates only visible Content in Application, revalidates history only after the stream completes, and persists exactly one final immutable Assistant message.

Lot 10B.1 introduces the immutable Application-level `GenerationSnapshot` as the first foundation for generation revisions and provenance. It captures only stable correlation and requested generation state: conversation identifier, triggering user-message identifier, UTC capture time, provider identifier, model reference, configured context size, and a defensive copy of provider-neutral generation options. It intentionally does not duplicate conversation content, provider telemetry, runtime diagnostics, reasoning, response text, or future provenance/context records. Unset values remain unset so Alicia preserves the existing provider/model-default semantics instead of inventing effective defaults.

Lot 10B.2 adds the immutable Application-level `GenerationProfileId` and `GenerationProfile` core. A profile captures reusable generation behavior through a stable UUID, normalized name, optional base system instructions, provider-neutral generation options, and immutable initial suggestions. The explicit built-in default profile carries no Alicia overrides and is distinguishable from custom profiles without introducing persistence or UI state. Model ownership, visual identity, working drafts, revisions, selection, and provenance remain separate later boundaries so the behavioral payload is not coupled to the current raw model-reference representation.

### Infrastructure

Implementations for provider APIs, persistence, operating-system services, networking, and other external boundaries. The local conversation slice provides versioned JSON document persistence, legacy document reads, recent-activity summary listing, deletion, detached aggregate reconstruction, and an explicit composition object for the lifecycle use cases. The provider slice implements an explicit `InferenceProviderRegistry`, a versioned atomic JSON configuration store, and the llama.cpp adapter. The registry maps stable provider identifiers to lifecycle runtimes and streaming responders and refuses implicit fallback. The llama.cpp slice detects CUDA-capable executables, builds the managed Linux x64 `llama-server` target from the official source release, reports installation progress, owns bounded managed-storage inspection/removal beneath its runtime root, launches `llama-server -hf` on a dynamically selected loopback port with localhost-only CORS, the bundled Web UI disabled, a per-process ephemeral API key supplied through the child environment, and an optional configured context size. It owns the process lifecycle/model cache/session secret, sends Bearer authentication on protected local HTTP calls, waits for public health readiness within a finite deadline, bounds health/ownership, installer, chat-header, stream-idle, and executable-probe waits, detects unexpected managed-process exit, verifies process ownership through authenticated `/props`, and maps OpenAI-compatible SSE responses into Application chunks. Raw HTTP bodies, server log tails, local paths, and process diagnostics remain Infrastructure diagnostics and are never used as provider user messages. Runtime maintenance treats `installation.json`, `releases/`, `.staging/`, and `logs/` as the runtime scope and `models/` as a separate cache scope; configuration/conversation data are not maintenance targets, deletion is root-confined, and directory links are removed without following their targets. Explicit request sampling options are serialized only when configured. The llama.cpp chat adapter also serializes explicit reasoning enable/disable and token-budget controls, requests the OpenAI-compatible final streamed usage chunk, parses usage/timing metadata separately from visible `content`/`reasoning_content`, and keeps provider-specific process/HTTP/CUDA details confined to Infrastructure. `LlamaCppProviderRuntime` measures end-to-end/first-output latency and maps completion, caller cancellation, or safe provider failure classification into the provider-neutral observation contract. A best-effort rotating JSONL observation log under the provider `logs/` directory stores only that structured observation type; it has no fields for request messages, prompts, reasoning, response text, raw HTTP bodies, API keys, endpoints, log tails, or exception diagnostics.

### Presentation

Shared Avalonia views and ViewModels for conversation history, selection, lifecycle actions, explicit provider/model settings, provider lifecycle controls and phase-aware installation progress, local user-message composition, message projection, empty/loading states, accessibility metadata, and user-facing error projection. Provider runtime state is projected separately from the last recoverable failure classification so a healthy `Ready` runtime can direct `Model` errors to Models or `Network` errors to a fresh provider check without suggesting reinstall. Managed storage maintenance is also projected separately: inspection is non-destructive, while cleanup/uninstall requests open an explicit confirmation surface and destructive actions are disabled while the provider is running. `ShellViewModel` owns global Conversations/Providers/Models workspace selection plus one shared `MainViewModel`. UIX-01 Stage 9 turns that shared `MainViewModel` into an orchestration/compatibility facade over six explicit Presentation slices: `ConversationWorkspaceViewModel`, `ConversationHistoryViewModel`, `ConversationStreamViewModel`, `ProviderViewModel`, `ModelViewModel`, and `GenerationSettingsViewModel`. State ownership and provider/model validation are therefore no longer concentrated in a single monolith, while existing bindings remain source-compatible during the refactor. `ShellView` is the Presentation root and renders a persistent 56 px icon-only global navigation rail with a delayed overlay label flyout. `MainView` is Conversation-only: its history surface supports title-first/message-content search, lazy three-message hover previews, persisted per-conversation icon/color identity, overflow/right-click Rename/Change icon/Change color/Delete actions, persisted collapse/reopen preference, and automatic narrow-layout collapse while provider and model controls remain exclusive to their dedicated global workspaces. UIX-01 Stage 8 adds a per-conversation `Following`/`Detached` scroll state machine, explicit pause/reattachment controls, layout-change-safe streaming behavior, and versioned non-domain UI-state persistence under an injected Presentation store. UIX-01 Stage 10A extends that same Presentation-only state boundary with icon/color history identity while retaining backward-compatible reads of the v1 UI-state document. UIX-01 Stage 10B adds a Presentation-only configuration gate that deterministically projects provider/model readiness into one recovery action; global workspace selection remains owned by `ShellViewModel`, which handles typed navigation requests from the shared conversation workspace. UIX-01 Stage 10C completes the Conversation responsive boundary: the persisted history preference applies to wide layouts, narrow layouts use an independent temporary overlay with a blocking backdrop, and destructive conversation deletion is confirmed through a root-level modal surface that prevents background pointer interaction. UIX-01 Stage 10D closes the foundation accessibility boundary: temporary history and delete surfaces own/cycle/restore keyboard focus, Escape dismisses those surfaces before generation cancellation, global/history selection is exposed through automation item status, and Reduced Motion also suppresses navigation dwell/indeterminate-progress motion while retaining textual live status. UI refinement Lot 10.7A is deliberately Presentation-only: Provider/Models markup uses a calmer hierarchy and progressive disclosure while preserving every existing command/binding and all Application/Infrastructure behavior. Lot 10.7 keeps observability subordinate to that hierarchy: the latest generation outcome/metrics are projected only inside the existing collapsed Provider Technical details disclosure and refreshed when a generation finishes, fails, or is cancelled. Presentation owns draft/focus/scroll behavior, persists the user message before starting response generation, projects a mutable Assistant-only streaming view model while Content and Reasoning deltas arrive, shows a first-delta thinking indicator with a Reduced Motion path plus a darker collapsible reasoning-step surface, briefly gates Stop/Retry against accidental early cancellation, removes partial projections on cancellation/failure, and reloads the persisted immutable message after successful completion while retaining only an in-memory reasoning snapshot for that projection. It does not select conversation persistence or responder implementations.

### Desktop

The desktop executable composition root for Windows, Linux, and macOS. It selects the local JSON conversation runtime, chooses platform-local data directories, supplies the Presentation UI-state path, probes a best-effort platform Reduced Motion preference, creates the managed `LlamaCppProviderRuntime`, registers it under a stable provider identifier, creates the global JSON configuration store with Lot 08 legacy-model migration, wires the registry into `StreamConversationTurnUseCase`, constructs the shared `MainViewModel`, wraps it in the Presentation `ShellViewModel`, injects that shell through the Presentation factory, disposes the managed server at shutdown, and starts Avalonia. Other hosts can make different platform/UI-state choices while reusing `Alicia.Presentation`.

## Dependency rules

- Domain has no internal project dependency.
- Application may depend on Domain only.
- Infrastructure may depend on Application and Domain.
- Presentation may depend on Application and Domain, but never Infrastructure.
- Desktop is the platform-specific composition root and may depend on Presentation and Infrastructure; it must not contain domain rules or persistence behavior.


### Retry boundary policy

Provider robustness distinguishes request replay safety from transport recoverability. Conversation generation POSTs are never replayed automatically because timeout or disconnect after request acceptance is ambiguous. Alicia only exposes the existing explicit user Retry for an unanswered persisted user message. Infrastructure may retry bounded transient failures only on idempotent HTTP GET boundaries such as release discovery, download response establishment, and session ownership probes; caller cancellation always aborts the retry/backoff immediately. llama-server readiness remains a bounded idempotent health poll.


Lot 10.5 separates the managed installed release, Alicia-validated pinned release, and upstream latest release; managed installation/update use the pinned source commit and atomically switch activation metadata only after candidate validation while retaining prior release directories.

Lot 10.6 separates managed runtime storage from the model cache and introduces explicit, confirmed cleanup/uninstall boundaries that preserve provider configuration and conversations.
