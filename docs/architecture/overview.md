# Architecture overview

## Goals

Alicia separates conversation rules, application orchestration, external AI/provider integrations, shared Avalonia presentation, and executable platform hosts.

## Layers

### Domain

Framework-independent domain concepts and invariants. The conversation core owns typed conversation/message identifiers, normalized titles, creation/activity metadata, message roles, immutable message data, and aggregate-level lifecycle invariants.

### Application

Use cases and ports for response generation, provider lifecycle management, persistence, clocks, files, search, tools, and other external capabilities. The conversation application slice exposes creation, loading, summary listing, renaming, message appending, deletion, the provider-neutral `IConversationResponder` and `IStreamingConversationResponder` response ports, non-streaming generation/completion, streamed turn orchestration, and an `IConversationRepository` persistence port without selecting an infrastructure implementation. `IInferenceProviderRuntime` exposes provider detect/install/start/stop state plus a provider-neutral installation-progress contract without referencing llama.cpp, CUDA, processes, or HTTP. Application also owns immutable provider descriptors/configuration, generation options, the `Missing/Unsupported/Faulted/Network/Model` failure taxonomy, a safe-message `InferenceProviderException`, an explicit provider-registry port, and a configuration-store port. Both turn paths are tied to the triggering user-message identifier and share snapshot validation. Streaming distinguishes provider-neutral Content and Reasoning chunks, forwards both to Presentation, accumulates only visible Content in Application, revalidates history only after the stream completes, and persists exactly one final immutable Assistant message.

### Infrastructure

Implementations for provider APIs, persistence, operating-system services, networking, and other external boundaries. The local conversation slice provides versioned JSON document persistence, legacy document reads, recent-activity summary listing, deletion, detached aggregate reconstruction, and an explicit composition object for the lifecycle use cases. The provider slice implements an explicit `InferenceProviderRegistry`, a versioned atomic JSON configuration store, and the llama.cpp adapter. The registry maps stable provider identifiers to lifecycle runtimes and streaming responders and refuses implicit fallback. The llama.cpp slice detects CUDA-capable executables, builds the managed Linux x64 `llama-server` target from the official source release, reports installation progress, launches `llama-server -hf` on a dynamically selected loopback port with localhost-only CORS, the bundled Web UI disabled, a per-process ephemeral API key supplied through the child environment, and an optional configured context size. It owns the process lifecycle/model cache/session secret, sends Bearer authentication on protected local HTTP calls, waits for public health readiness within a finite deadline, bounds health/ownership, installer, chat-header, stream-idle, and executable-probe waits, detects unexpected managed-process exit, verifies process ownership through authenticated `/props`, and maps OpenAI-compatible SSE responses into Application chunks. Raw HTTP bodies, server log tails, local paths, and process diagnostics remain Infrastructure diagnostics and are never used as provider user messages. Explicit request sampling options are serialized only when configured. The llama.cpp chat adapter also serializes explicit reasoning enable/disable and token-budget controls, parses OpenAI-compatible `reasoning_content` separately from visible `content`, and keeps provider-specific process/HTTP/CUDA details confined to Infrastructure.

### Presentation

Shared Avalonia views and ViewModels for conversation history, selection, lifecycle actions, explicit provider/model settings, provider lifecycle controls and phase-aware installation progress, local user-message composition, message projection, empty/loading states, accessibility metadata, and user-facing error projection. Provider runtime state is projected separately from the last recoverable failure classification so a healthy `Ready` runtime can direct `Model` errors to Models or `Network` errors to a fresh provider check without suggesting reinstall. `ShellViewModel` owns global Conversations/Providers/Models workspace selection plus one shared `MainViewModel`. UIX-01 Stage 9 turns that shared `MainViewModel` into an orchestration/compatibility facade over six explicit Presentation slices: `ConversationWorkspaceViewModel`, `ConversationHistoryViewModel`, `ConversationStreamViewModel`, `ProviderViewModel`, `ModelViewModel`, and `GenerationSettingsViewModel`. State ownership and provider/model validation are therefore no longer concentrated in a single monolith, while existing bindings remain source-compatible during the refactor. `ShellView` is the Presentation root and renders a persistent 56 px icon-only global navigation rail with a delayed overlay label flyout. `MainView` is Conversation-only: its history surface supports title-first/message-content search, lazy three-message hover previews, persisted per-conversation icon/color identity, overflow/right-click Rename/Change icon/Change color/Delete actions, persisted collapse/reopen preference, and automatic narrow-layout collapse while provider and model controls remain exclusive to their dedicated global workspaces. UIX-01 Stage 8 adds a per-conversation `Following`/`Detached` scroll state machine, explicit pause/reattachment controls, layout-change-safe streaming behavior, and versioned non-domain UI-state persistence under an injected Presentation store. UIX-01 Stage 10A extends that same Presentation-only state boundary with icon/color history identity while retaining backward-compatible reads of the v1 UI-state document. UIX-01 Stage 10B adds a Presentation-only configuration gate that deterministically projects provider/model readiness into one recovery action; global workspace selection remains owned by `ShellViewModel`, which handles typed navigation requests from the shared conversation workspace. UIX-01 Stage 10C completes the Conversation responsive boundary: the persisted history preference applies to wide layouts, narrow layouts use an independent temporary overlay with a blocking backdrop, and destructive conversation deletion is confirmed through a root-level modal surface that prevents background pointer interaction. UIX-01 Stage 10D closes the foundation accessibility boundary: temporary history and delete surfaces own/cycle/restore keyboard focus, Escape dismisses those surfaces before generation cancellation, global/history selection is exposed through automation item status, and Reduced Motion also suppresses navigation dwell/indeterminate-progress motion while retaining textual live status. Presentation owns draft/focus/scroll behavior, persists the user message before starting response generation, projects a mutable Assistant-only streaming view model while Content and Reasoning deltas arrive, shows a first-delta thinking indicator with a Reduced Motion path plus a darker collapsible reasoning-step surface, briefly gates Stop/Retry against accidental early cancellation, removes partial projections on cancellation/failure, and reloads the persisted immutable message after successful completion while retaining only an in-memory reasoning snapshot for that projection. It does not select conversation persistence or responder implementations.

### Desktop

The desktop executable composition root for Windows, Linux, and macOS. It selects the local JSON conversation runtime, chooses platform-local data directories, supplies the Presentation UI-state path, probes a best-effort platform Reduced Motion preference, creates the managed `LlamaCppProviderRuntime`, registers it under a stable provider identifier, creates the global JSON configuration store with Lot 08 legacy-model migration, wires the registry into `StreamConversationTurnUseCase`, constructs the shared `MainViewModel`, wraps it in the Presentation `ShellViewModel`, injects that shell through the Presentation factory, disposes the managed server at shutdown, and starts Avalonia. Other hosts can make different platform/UI-state choices while reusing `Alicia.Presentation`.

## Dependency rules

- Domain has no internal project dependency.
- Application may depend on Domain only.
- Infrastructure may depend on Application and Domain.
- Presentation may depend on Application and Domain, but never Infrastructure.
- Desktop is the platform-specific composition root and may depend on Presentation and Infrastructure; it must not contain domain rules or persistence behavior.
