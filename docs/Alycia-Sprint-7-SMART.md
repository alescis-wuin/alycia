## 1. SMART Objective

**Objective:** enable an uninitialized Alycia instance's sole owner to create the local account **once**, through Avalonia using a secret generated by a local administrative command, and **atomically** assign every existing S6 Workspace to that account, with no public signup or inherited anonymous business access.

- **Specific:** single-owner Identity domain, dedicated repository/DbContext and migrations, time-limited bootstrap secret, protected local HTTP bootstrap endpoint, Avalonia form, joint account-and-Workspace transaction and second-owner denial.
- **Measurable:** 11 acceptance criteria AC01–AC11 evidenced by input validation, concurrency, failure, local-network access, restart and PostgreSQL persistence checks; a real end-to-end demonstration in a controlled environment.
- **Achievable:** reuse .NET 10, PostgreSQL, API, Avalonia, logging and `make migrate` **only after verifying their actual post-S6 availability and S6 closure**; never presume unmerged S6 code exists.
- **Relevant:** establish Workspace ownership and sole-owner bootstrap before S8 login/effective logout and S9 per-device sessions.
- **Time-bounded:** roughly 6–9 indicative sessions of 45–90 minutes; continue the sprint if criteria remain unmet rather than close it artificially.

**Final demonstration:** on an **isolated test database**, an existing S6 Workspace remains in storage; a valid local secret lets Avalonia create the sole owner; all existing Workspaces are attached in the transaction; the secret is then unusable, a second owner bootstrap is refused and data remain consistent after restart.

## 2. Prerequisites, Decisions and Security Boundaries

- **Absolute start prerequisite:** Sprint 6 actually complete and merged into `develop`; satisfied issues manually closed; actual S6 END, criteria and local HEAD verified. Do not change any S6 SMART or startup kit while preparing S7.
- **S7 preparatory decisions (`S7-01`–`S7-07`): APPROVED.** See `Alycia-Sprint-7-Arbitrages-prealables.md`.
- **Future User/Workspace model:** `User.Id: Guid`, normalized `LoginIdentifier: string`, and `Workspace.OwnerUserId: Guid` added **only after S6**; no physical cross-module FK. `User.CreatedAtUtc` remains a candidate unless approved as part of the complete SMART.
- **S7-01/02/03 — APPROVED:** an explicit local administrative command generates a cryptographically secure 256-bit one-use secret, valid for 15 minutes. At most **five presentations of an incorrect secret** are allowed; missing secrets and other invalid form fields with a correct secret do not consume the counter. The counter persists safely across concurrency and restarts. After expiry or lockout, a new local admin command may issue a replacement, invalidating its predecessor and starting **a new counter at zero**; **at most one active secret**, with no reissue after initialization. The HTTP bootstrap endpoint remains loopback-only and permanently unusable after success.
- **S7-04:** 3–64 ASCII-character login identifier matching `[A-Za-z0-9._-]`, case-insensitive comparison and stable normalized representation.
- **S7-05 — APPROVED AMENDMENT (policy B):** password length **15–128 Unicode code points after NFC normalization**, including spaces and printable Unicode characters; **no mandatory character-category composition**. Check the full password against a **documented local list of common or compromised passwords**, never sending it to a third party. Do not truncate, silently remove spaces, or change the password beyond the disclosed NFC normalization. This owner-approved requirement supersedes the old 12–128/category policy and proposed “3 out of 4” rule; it is part of the approved complete SMART.
- **S7-06:** `IdentityDbContext` and dedicated Identity repository with own Infrastructure migrations integrated into the centralized explicit `make migrate`; `PasswordHasher<User>` without introducing the full ASP.NET Core Identity data model. Application uses ports, and the concrete hasher stays in Infrastructure.
- **MODEL-E01/E02:** a **shared PostgreSQL transaction** between Identity and Workspaces, coordinated **outside the business domains/services**, with full rollback of the business initialization transaction on error. Explicit per-module schema migrations are prerequisites and **do not become an all-module atomic deployment transaction**.
- **Inherited security:** S6's anonymous Workspace exception is limited to S6; S7 does not extend it. Until S8 implements normal authentication, expose no normal anonymous business-resource access; S7 does **not issue a login session** following bootstrap.
- **Docker restriction:** publishing a host port on `127.0.0.1` is necessary but **not enough** to block internal Docker peers; effective isolation must be implemented and tested.
- **MAUI:** temporarily deferred on Linux; do not close the Authentication/Sessions MVP capability before Windows parity and the relevant S8–S9 slices are actually complete.

## 3. Included Scope

1. Define `User` in `Identity.Domain` with Guid ID, normalized local login identifier, single-owner and naming invariants, without public account registration or multiuser roles.
2. Implement bootstrap use cases and a dedicated account repository port in `Identity.Application`; implement EF Core/PostgreSQL persistence in `Identity.Infrastructure`, keeping the domain free of EF and authentication framework dependencies.
3. Add Identity-owned migrations and a post-S6 `Workspace.OwnerUserId` schema evolution; apply migrations only via the **explicit** central `make migrate` entry point with documented order, idempotence and stop-on-error. No automatic `Database.Migrate()` at startup.
4. Safely orchestrate a **shared PostgreSQL transaction** across both contexts without business modules directly accessing each other's DbContexts, enforce only one owner under concurrency, attach all pre-existing Workspaces in the same transaction and allow safe retry after rollback.
5. Provide an explicit local administrative command creating a cryptographically secure 256-bit temporary secret; store at most its protected verifier and expiry/incorrect-secret-attempt metadata. Preserve the counter across restarts; after expiry or lockout allow secure local admin regeneration that invalidates the prior secret, starts **a fresh zeroed counter** and keeps **only one secret active**. After successful initialization, prohibit any regeneration. Never include the raw secret in logs, tracked files or diagnostic responses.
6. Expose the HTTP bootstrap workflow exclusively on local loopback, enforcing a required secret, expiry, **lockout after five incorrect-secret presentations**, one-time use and permanent closure after success; do not count other invalid form fields after a correct secret. Verify nonlocal and Docker-peer denial, including a local Production configuration.
7. Apply the standard application JSON envelope to non-streaming responses (`success,status,code,message,data,errors,traceId,timestamp`), matching HTTP statuses, validation, error handling and trace correlation without disclosing secrets or detailed sensitive rejection reasons.
8. Add an Avalonia initial-owner form with secret, username, password and confirmation; loading/success/error/unavailable states, feedback on a common/compromised password, and length validation without composition rules. Do not persist sensitive form data or invent S8 auto-login.
9. Document the local bootstrap procedure in English, including secret handling, migrations, network restrictions, failure recovery, Workspace attachment and limitations; demonstrate using non-sensitive isolated test data.
10. Provide a reviewed English SMART, factual English pre-PR END, real issues and AC checklists; signed commits and PR review following the Charter.

## 4. Excluded Scope

- Normal login, effective logout, access-token issuance, refresh tokens, persistent/revocable per-device sessions (**S8–S9**).
- Public signup, second owner, collaboration/multiuser accounts, owner replacement, full credential recovery or unapproved password-reset mechanisms.
- Changes to S6 SMART, issues or implementation before S6 closure; rewriting its historical END.
- New Workspace create/edit/delete features, Project, Conversations, Providers, Knowledge, Secrets or RAG functionality.
- LAN/VPN bootstrap exposure, expanding the S6 exception, or retaining a usable bootstrap after initialization.
- MAUI/Windows during the Linux slice, vault, CI/CD, advanced monitoring, releases or promotion to `testing`/`main`.

## 9. Test and Verification Strategy

- **Unit tests:** login character/length bounds and case-insensitive normalization; password **15–128 after NFC, spaces/Unicode, no composition and local blocked-password list**, confirmation; second-owner denial, incorrect-secret-only counting and bootstrap state transitions.
- **Mandatory PostgreSQL integration:** isolated test DB migration/twice, concurrent constraints, pre-existing S6 Workspaces, shared transaction, injected rollback, absence of orphan Workspaces, restart and duplicate initialization.
- **Local security:** missing/invalid/expired secret, five incorrect-secret presentations, correct secret with invalid form, persistent counter and local admin regeneration after expiry/lockout, reuse; no sensitive data in logs/responses, real nonlocal denial, second Docker-container test, no extension of anonymous S6 routes.
- **Avalonia UI:** four fields, confirmation, validation and unavailable state, retry, success and no fictional authenticated session.
- **Quality:** necessary builds, `make check`, focused diff and redacted evidence; stop when relevant tests pass unless changed code or concrete uncertainty.
- **Database safety:** never purge/reset the owner's real Workspaces without explicit authorization; use an isolated test environment.
